00:00Problem definition

Amazon Locker

Amazon is an online retailer that allows customers to order products for delivery. Sometimes customers are unavailable at their usual address to receive packages. In such cases, Amazon provides a secure, automated pickup and return service called Amazon Locker.

Amazon Lockers are available at various locations, each containing multiple lockers of different sizes and operating hours. Customers can select a nearby locker location for delivery or returns. Only packages that fit a locker's size are eligible. When a package arrives, the customer receives a unique code to retrieve it. Packages are stored for a limited period; if uncollected, they are removed, and the customer may be refunded. Customers can also return eligible products by dropping them off at available locker locations, where the logistics team picks them up.

What makes it interesting

  • Real-time resource allocation: lockers are scarce and physical
  • Concurrent requests for the same locker
  • Operating-hour constraints on top of a time limit
  • Physical sizes: packages must fit lockers
  • Two flows sharing one resource: delivery and return

You will be asked to

  • Assign lockers to orders and returns by size and availability
  • Handle pickups, returns and uncollected items
  • Manage locker states, codes and access windows
  • Make it work reliably and securely at scale
00:03Expectations from the interviewee

What the interviewer wants to hear

In the interview, you are expected to

  1. Clarify requirements, constraints and edge cases by asking relevant questions.
  2. Identify and design the core components.
  3. Justify every decision with OOD and SOLID principles.

The four areas you must probe

  • Locker size: sizes, package fit, restrictions
  • Locker selection: who chooses, how two customers never share one, two orders at once
  • Locker status: time limit, what happens after it
  • Returning an item: allowed? same locker? how assigned?

How you're scored

  • Scoping before designing
  • Decomposition: entities you can name in one phrase
  • Responsibility placement: behaviour next to the data it protects
  • Extensibility: a new rule is a new class, not five edited ifs
  • Patterns with a reason, including choosing not to use one
  • Failure thinking: full location, wrong code, two customers, expired
  • Communication: narrate, draw, invite pushback
00:05Clarifying questions

The questions, and what they buy you

  • Are there different locker sizes? How does package size affect assignment? Restrictions on what can be stored?
  • Will the customer choose the locker, or does the system assign one by availability?
  • How will the system ensure two customers don't get the same locker?
  • Can a customer get two lockers for different orders at the same time? Does one order ever need two lockers?
  • Is there a time constraint? What happens if the customer doesn't come?
  • Can the customer return an item through a locker? Same locker? How is it assigned?
00:15Requirements

R1 to R12

ReqRequirement
R1Customers select a preferred locker location for pickup during checkout.
R2An order has one or more items; items are packaged together where locker sizes allow.
R3Locations contain lockers of six sizes: XS, S, M, L, XL, XXL.
R4Only packages that fit fully inside a locker's interior are eligible.
R5On delivery the customer receives a unique 6-digit code to open the locker.
R6Packages are held for three days.
R7Pickup must happen within the 3-day window and the location's operating hours.
R8Uncollected after three days: removed, locker released, customer refunded.
R9Each locker is assigned to one customer/package at a time.
R10After collection the locker is locked and the code is invalidated, never reused.
R11Returns: choose a location, get a locker by size, receive a new code to drop the item.
R12Logistics collects returns with its own code; customer notified; refund per product eligibility.

Every design decision from here on is traced back to one of these labels. If a class doesn't serve an R, ask why it exists.

00:27Design approach: bottom-up

Entities first, then the flows over them

Core entities

  • LockerLocation · a place with lockers and opening hours
  • Locker · one door, one size, one state
  • Customer, Item, Order · what was bought and where it should go
  • Package · items boxed together; the thing that has to fit
  • LockerPackage · a package's stay in a locker: code, deadline, status
  • ReturnPackage · an item's way back: two codes, two actors
  • AccessCode · 6 digits, valid until, single use
  • LockerService · the flows

Bottom-up means: get the nouns and their invariants right, and the flows become short.

01:00Steps 1 and 2 · R3R4

Sizes, states, and a value object that knows about rotation

step 2 LockerSize with interior dimensions, LockerState, Dimensions value object

  • Six sizes in ascending order, each with interior dimensions, so "smallest that fits" is a scan.
  • Four locker states: AVAILABLE, BOOKED, OCCUPIED, OUT_OF_SERVICE.
  • Dimensions.fitsIn() owns the rule "fits fully inside", in any orientation.
01:04Step 3 · R1R2R4

Order, Package, and who decides what goes in a box

step 3 Customer, Item, Order, Package and PackagingService

  • The order carries the locker location chosen at checkout.
  • A Package is items boxed together with dimensions of its own; the box is what has to fit.
  • PackagingService turns an order into packages and rejects an item that fits no locker at all.
01:08Step 4 · R3R7R9

A locker is a row. A location is built, not constructed.

step 4 Locker, OperatingHours, LockerLocation with a Builder

  • Locker: id, size, state, what it's assigned to, and a version number.
  • OperatingHours answers one question: is it open at this time?
  • LockerLocation is created through a Builder; a location without lockers or a name cannot exist.
01:12Step 5 · R4R9

Two customers, one locker, the same instant

step 5 LockerRepository with atomic book(), assignment strategy, race demo

NAIVE   findAvailable → await → save
  A booked L1-M-1
  B booked L1-M-1
  locker L1-M-1 is BOOKED, assigned to LP-B

ATOMIC  rank → compare-and-set book()
  A booked L1-M-1
  B rejected: No available locker at L1 fits a 40x30x20 cm package
  locker L1-M-1 is BOOKED, assigned to LP-A
  • The strategy ranks the available lockers that fit: smallest first.
  • The repository's book() succeeds only if the locker is still AVAILABLE at the version we read.
  • The assigner tries each candidate until one booking succeeds.
01:18Step 6 · R5R6R10

A code that expires, a package that knows what's legal

step 6 AccessCode and the LockerPackage state machine

  • AccessCode: 6 digits from a secure random source, valid until a date, compared in constant time.
  • LockerPackage moves BOOKED → DELIVERED → PICKED_UP, or DELIVERED → EXPIRED → REMOVED. Each state is a class.
  • Pickup with the right code destroys the code. It cannot be reused.
01:24Step 7 · R5R6R7R8R10

The delivery flow, end to end

step 7 delivery flow: LockerService, notifications as observers, clock, demo

  • LockerService sequences: assign lockers → deliver → pick up → process expired.
  • Time comes from an injected Clock, so three days can be tested.
  • The service emits events; a CustomerNotifier turns them into emails. The service never mentions email.
01:30Step 8 · R11R12

Returns: the same shape, roles swapped, nothing else touched

step 8 return flow: ReturnPackage, two codes, refund per product

  • The customer's code opens the locker to drop the item. It dies on use; a logistics code is born.
  • Logistics collects with its own code. The locker is released; the refund follows the product's eligibility.
  • The delivery flow did not change. The assigner, repository, codes and events were reused as they were.
01:34Step 9 · tests

Thirteen tests, no framework, every dependency a fake

step 9 tests for assignment, packaging, concurrency and every service flow

✔ R5/R10: booked → delivered issues a code; pickup clears it; cannot be reused
✔ wrong code is rejected without changing state
✔ R6/R8: valid until exactly three days; expiry illegal before, legal at the boundary
✔ R4: dimensions fit in any orientation
✔ R4: smallest-fit ranks the smallest locker the package fits first
✔ R9: two concurrent assignments for the last fitting locker: exactly one wins
✔ a small package falls through to a bigger locker when the small one is taken
✔ R2: items are boxed together when they fit; a box never exceeds the largest locker
✔ R1-R5: order → packed → locker booked → delivered → customer emailed the code
✔ R7/R10: pickup only in opening hours; code single-use; locker released
✔ R6/R8: after three days: removed, locker released, customer refunded
✔ R11/R12: return uses two codes; refund follows product eligibility
✔ an order needing two lockers when only one fits is rolled back entirely
ℹ tests 13  pass 13  fail 0
  • Test names carry the requirement label. The suite is the requirements, executable.
  • FixedClock, FixedCodeGenerator, RecordingChannel: the three fakes that make time, randomness and email testable.

01:43Most-asked LLD interview questions · general

The questions every LLD round asks, in some form

  • 1 · What is the difference between LLD and HLD? Which one are we doing when we argue about class names?
  • 2 · Explain SOLID with one violation each from real code.
  • 3 · Composition vs inheritance: when is inheritance right?
  • 4 · Strategy vs State. They look identical.
  • 5 · Adapter vs Facade vs Decorator vs Proxy.
  • 6 · Why "favour composition", why "program to an interface", why "dependency injection"? In one breath.
  • 7 · What is the Law of Demeter, and is order.customer.email a violation?
  • 8 · Singleton: why is it the pattern everyone has used and nobody defends?
  • 9 · When is DRY wrong?
  • 10 · How do you handle concurrency in an LLD? Node is single-threaded.
  • 11 · What is an anemic domain model, and how do you fix one?
  • 12 · How do you make time testable?
